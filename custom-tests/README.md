# Custom Tests

Example Drata Advanced Test Builder JSON for this OCI Custom Connection.
Paste into Monitoring > Create test > Advanced editor, after selecting
this connection's uploaded record as the data source.

- `admin-port-exposure.json` -- fails if any `resources.instances[].effectiveIngressExposure != not_exposed`. Mirrors `OCI-COMPUTE-ADMIN-PORT-EXPOSURE`.
- `autonomous-db-public-endpoint.json` -- fails if any `resources.autonomousDatabases[].publicEndpointPresent != false`. Mirrors `OCI-ADB-PUBLIC-ENDPOINT-PRESENT`.
- `customer-managed-key-volumes.json` -- fails if any *attached* `resources.bootVolumes[]`/`blockVolumes[].customerManagedKeyPresent != true`. Unattached volumes (`attachedInstanceIds` empty) are exempted in-JSON via a nested `any`, matching the real collector's own scoping (`aggregate.py`: `[v for v in (*boot_volumes, *block_volumes) if v.attached_instance_ids]`). Mirrors `OCI-STORAGE-CUSTOMER-MANAGED-KEY`; only meaningful when `decisions.requireCustomerManagedVolumeKeys` is enabled for this deployment.
- `customer-managed-key-databases.json` -- fails if any `resources.databases[]`/`autonomousDatabases[].kmsKeyId` is null. Mirrors `OCI-DATABASE-CUSTOMER-MANAGED-KEY`; only meaningful when `decisions.requireCustomerManagedDatabaseKeys` is enabled.
- `vpn-tunnel-redundancy.json` -- fails if any `resources.ipsecConnections[].redundancyStatus != redundant`. Mirrors `OCI-VPN-TUNNEL-REDUNDANCY`.
- `snapshot-completeness.json` -- fails unless top-level `snapshotStatus == complete`.
- `snapshot-freshness.json` -- genuinely dynamic rolling check: `collectedAt` `withinLastHours` the record's own `freshnessThresholdHours` (fact-to-fact comparison), re-evaluated against "now" on every test run.
- `inaccessible-compartments.json` -- fails if any top-level `warnings[].code == "COMPARTMENT_INACCESSIBLE"`. Catches compartments OCI marked not-accessible during discovery (`discovery.py`: `is_accessible` on the `list_compartments` response) -- a scope gap that does not flip `snapshotStatus` away from `complete` and is not surfaced by any other test in this set.

## Iteration 2 research notes (operators, nesting, filtering)

Five issues were open after iteration 1. Each was chased down against Drata's own help docs, product source (`[internal-repo]`, `[internal-repo]`, `[internal-repo]` on GitHub, via internal code search), and support/engineering tickets. Verdicts below.

1. **`notEqual` operator -- CONFIRMED.** `notEqual` is a real, documented operator, not a guess. Drata's engine defines it directly: `[internal-repo]` `packages/json-rules-engine/src/engine-default-operators.ts` builds its operator dispatch table keyed by `[Operator.notEqual]`, and the UI operator-label maps (`[internal-repo]` `views/monitoring-builder/src/lib/constants/operator.constant.ts`, and `[internal-repo]` `src/constants/monitorRecipe.constants.js`) both list `notEqual` -> "Not Equals" as a customer-selectable operator. A real, confirmed-working production Advanced Editor recipe (Jira [internal-ticket], Azure NSG ingress-rule test) uses `"operator": "notEqual"` four times, with a Drata engineer's own note: "I tested it and it works as expected." `customer-managed-key-databases.json`'s use of `notEqual` for `kmsKeyId != null` is correct as-is.

2. **`equal` vs `equals` -- RESOLVED: `equal` (singular) is correct.** This one is genuinely confusing because Drata's own TypeScript enum *member* is spelled `Operator.equals`, but its serialized wire value -- the actual string that belongs in the JSON `"operator"` field -- is `"equal"`. Definitive, single-source confirmation: a `[internal-repo]` PR ([internal-ref], reviewed against `[internal-package]@0.5.46`) states outright: `Confirmed require('[internal-package]').Operator.equals === 'equal' against the installed 0.5.46`, and a reviewer comment on the same PR independently confirms "it is a string enum whose `equals` member is `'equal'`". The actual engine source (`engine-default-operators.ts`) keys its operator map with `[Operator.equals]`, i.e. the literal string `"equal"`. Drata's own "Advanced Editor in the Test Builder" help article is internally inconsistent (uses `"operator": "equal"` five times across its JSON examples, and `"operator": "equals"` once, in the same article) -- that one "equals" instance is the outlier/typo, not the rule. All 7 files in this repo already use `"equal"` (singular); no changes were needed.

3. **`fact` + `path` landing on an array before an `all` quantifier -- CONFIRMED with a literal composed example.** Found real, shipped Drata Test Library recipes that combine an object hop (`path`) with a nested array quantifier in exactly the shape this repo uses:
   - Test 310, "Audit Logs Enabled for EKS Clusters": `{ fact: 'logging', path: 'clusterLogging', operator: Operator.all, value: { fact: 'enabled', operator: Operator.equals, value: true } }` -- `logging` is an object, `clusterLogging` is its nested array property, `all` quantifies over that array.
   - Test 130, "Load Balancer Used": `{ fact: '!SameRegionResources', path: 'ElasticComputeCloudInstances', operator: Operator.all, value: { fact: 'State', path: 'Name', operator: Operator.notEqual, value: 'running' } }` -- same shape, with a further `path` inside the per-item condition too.
   Both are real production recipe source (internal "Rebuilt AA / AP2 recipes" reference). This confirms the `{"fact": "resources", "path": "instances", "operator": "all", "value": {...}}` pattern used in 5 of these 7 files is correct as written; no changes were made.

4. **Relative-date / rolling-freshness operator -- CONFIRMED and applied.** Drata's engine has real relative-date operators anchored to `Date.now()`: `withinLastDays`, `withinNextDays`, `withinLastHours`, `olderThanDays` (`[internal-repo]` `packages/json-rules-engine/src/engine-default-operators.spec.ts`; shipped to the customer-facing test builder per `[internal-repo]` PR "chore(package): add new withinLastHours operator [[internal-ticket]]"). `withinLastHours` is listed as a customer-facing operator option ("Within Last (Hours)") in Drata's own CSM-facing custom-test prompt guide. `snapshot-freshness.json` now uses `{"fact": "collectedAt", "operator": "withinLastHours", "value": {"fact": "freshnessThresholdHours"}}`. Two confidence tiers here, stated plainly:
   - The `withinLastHours` operator itself, as a customer-facing Advanced Editor operator, is fully confirmed.
   - The `value` being a fact-to-fact reference (`{"fact": "freshnessThresholdHours"}`, so the threshold always tracks this record's own configured value instead of a second hardcoded number) is confirmed at the shared engine/type level: `[internal-repo]` `packages/json-rules-engine/src/condition.ts` has an explicit `isFactValue` check and resolves such a `value` via `almanac.factValue(...)`, and the recipe validator (`validate-recipe.ts` / `validate-recipe.spec.ts`) has dedicated `validateValueFactChain` / `validateValueTypeSupported` checks specifically for this case. Custom Tests and built-in Test Library tests are evaluated by this same engine and the same `@drata/types/recipe` condition shape, so this should carry over -- but there isn't a literal Custom-Test-specific example of it in the docs, so treat it as "engine-confirmed, not example-confirmed in a customer test." If the Advanced Editor UI ever rejects the fact-to-fact `value` on save, the documented fallback is a plain literal, e.g. `"value": 24`, matching this deployment's configured `decisions.freshnessHours` -- still a real dynamic (relative-to-now) check, just with the threshold duplicated instead of linked.

5. **Filtering Criteria for attached-only volume scoping -- RESOLVED, but not via Filtering Criteria; via the same in-JSON quantifier mechanic instead.** Filtering Criteria *is* JSON-expressible (not a picker-only UI dead end) -- confirmed via Jira [internal-ticket] and [internal-ticket] and `[internal-repo]` `views/monitoring-builder/src/lib/models/monitoring-edit-form.model.tsx` (`resource.filteringCriteria.evaluator`, same `all`/`any`/`fact`/`path`/`operator`/`value` grammar). However, it lives in its own separate "Add Filtering Criteria" code block per condition group -- a second JSON payload, not a key you can fold into the single evaluator JSON these files represent -- and, more importantly, it filters which *top-level resource records* a condition group evaluates. This connection publishes one snapshot record per run (single resource instance, per `oci-snapshot-1.0.0.json`), so Filtering Criteria could only ever include/exclude that one record wholesale; it has no way to reach into and filter individual items of a nested array like `bootVolumes`/`blockVolumes`. So Filtering Criteria is confirmed real but inapplicable to this specific problem regardless of JSON support. The actual fix: `customer-managed-key-volumes.json` now scopes attached-only directly inside the existing per-item quantifier, using the same `path`-to-a-scalar mechanic confirmed real in issue 3/4's evidence (e.g. Drata's own `path: 'length'` + `operator: equal` pattern, seen in production recipes for "Public SSH Denied" and "Load Balancer Used"):
   ```json
   { "any": [
       { "fact": "attachedInstanceIds", "path": "length", "operator": "equal", "value": 0 },
       { "fact": "customerManagedKeyPresent", "operator": "equal", "value": true }
   ] }
   ```
   This exempts unattached volumes (`attachedInstanceIds` empty) and requires a customer-managed key only for attached ones -- matching the real collector's own scoping in `src/oci_drata/transform/aggregate.py` (`[v for v in (*boot_volumes, *block_volumes) if v.attached_instance_ids]`), which is exactly what iteration 1 flagged as missing.

## Iteration 3 research notes (adversarial re-verification, coverage)

1. **`snapshot-freshness.json`'s fact-to-fact `value` -- confidence upgraded, still not a byte-identical customer example.** Iteration 2 left this "engine-confirmed, not example-confirmed": `condition.ts`'s `isFactValue` check and `validate-recipe.ts`'s `validateValueFactChain` prove the engine *can* resolve a `value` of `{"fact": ...}`, but no literal example existed anywhere in the trail. Two further pieces of evidence found this iteration, both outside engine source:
   - Two real, shipped Drata Test Library recipes use exactly this wire shape: Test 87 ("MFA on Version Control System") and Test 94 ("Version Control Accounts Removed Properly"), both GITHUB-provider recipes (internal "AP2 Recipes" reference), each with a condition like `{ fact: '!DrataUser', path: 'personnel.startDate', operator: Operator.isAfter, value: { fact: '!DrataPolicySLAEarliestDate', params: {...} } }` -- a bare `{fact: ...}` object as `value`, evaluated in production by the same engine and condition grammar as Custom Tests.
   - A real customer-facing bug ticket for a customer-authored Advanced Editor Custom Test (Jira [internal-ticket], [customer] tenant, AWS IAM Password Reuse test) surfaces the backend's actual runtime validation error text: `"Value of type 'string' is not within supported types: number, null, fact"`. This is `validate-recipe.ts`'s type check firing on a real customer save request, and it lists `fact` as one of only three valid `value` types -- proof the fact-to-fact branch is live and reachable from the customer-facing save path, not just declared in source.
   - Caveat: both are Drata-authored Test Library recipes with a parameterized custom fact (`!`-prefixed, with `params`) as the referenced value, not a customer-typed Advanced Editor example referencing a plain sibling field the way `{"fact": "freshnessThresholdHours"}` does. No literal example of *that* exact shape (bare same-record field self-reference) turned up.
   - Net effect: `snapshot-freshness.json` is unchanged (still `{"fact": "collectedAt", "operator": "withinLastHours", "value": {"fact": "freshnessThresholdHours"}}`), and the fallback noted in iteration 2 (a plain literal `value`, e.g. `24`) still stands if the Advanced Editor UI ever rejects it on save -- but the working assumption is now backed by a live customer error path and shipped recipe examples, not engine/type source alone.

2. **Adversarial re-check of `notEqual` -- held up, and found a tighter match than iteration 2 had.** Iteration 2's confirmation of `notEqual` came from a customer NSG test comparing strings. This iteration specifically tried to break the exact pattern `customer-managed-key-databases.json` relies on -- `notEqual` compared against a literal JSON `null` -- by searching for known bugs or edge cases in `notEqual` vs. `null`/undefined. None turned up: `engine-default-operators.spec.ts` shows a plain strict-inequality implementation (`assess('a','b') -> true`, `assess(10,10) -> false`), with no special-cased null handling to go wrong. Better still, a real shipped Drata Test Library recipe (Test 95, "Infrastructure Accounts Properly Removed") uses the identical pattern: `{ fact: '!DrataUserIdentity', path: 'disconnectedAt', operator: Operator.notEqual, value: null }`. No fix needed; `customer-managed-key-databases.json` is unchanged.

3. **Coverage check against `oci-snapshot-1.0.0.json` and `findings.py`.** Evaluated several candidates before settling on one addition:
   - `metrics.exadataDetectedCount` and `manifest.unresolvedRelationships` -- traced through `src/oci_drata/validation/completeness.py`'s `decide_completeness()`: both `exadata_detected` and `unresolved_relationship_count > 0` unconditionally force `snapshotStatus` to `incomplete`. A Custom Test on either would always agree with `snapshot-completeness.json`'s existing `snapshotStatus == complete` check -- not genuinely distinct, so neither was added.
   - `metrics.collectionErrorCount` -- traced through `operations_complete()` (`src/oci_drata/pagination.py`): any operation with `status == "failed"` makes its owning domain's `.complete` false, which `decide_completeness()` also turns into `incomplete`. Same conclusion: fully redundant with `snapshot-completeness.json`.
   - Lifecycle-excluded resources (`warnings[].code == "LIFECYCLE_EXCLUDED"`, severity `info`) -- these are expected, deliberate exclusions (`src/oci_drata/transform/lifecycle.py`) of resources that are genuinely gone (terminated/terminating), not a coverage gap. A test that fails on their presence would false-positive on ordinary infrastructure churn, so this was rejected as a test candidate.
   - `warnings[].code == "COMPARTMENT_INACCESSIBLE"` (severity `warning`) -- traced through `src/oci_drata/collection/discovery.py`: this fires when OCI itself marks a compartment `is_accessible: false` on the `list_compartments` response. That path never marks any operation `failed`, is never read by `discovery.complete` (`not unready_regions and operations_complete(...)`) or by `decide_completeness()`, so a tenancy can have compartments the collector's IAM policy cannot see into and still get `snapshotStatus == complete`. None of the other 7 tests, nor `snapshot-completeness.json`, can ever catch this. Added `inaccessible-compartments.json` for it.
